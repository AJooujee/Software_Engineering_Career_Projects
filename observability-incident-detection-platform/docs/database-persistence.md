# Database Persistence and Service Registry

## Overview

Phase 3 replaces temporary in-memory telemetry storage with asynchronous
PostgreSQL persistence. It also introduces a service registry so every
telemetry record belongs to a known monitored service and environment.

## Technology

- PostgreSQL 17
- Docker Compose
- SQLAlchemy 2 asynchronous ORM
- asyncpg
- Alembic
- aiosqlite for isolated automated tests

## Local Database

Start PostgreSQL:

```powershell
docker compose up -d postgres
```

Check its status:

```powershell
docker compose ps
```

Stop the container:

```powershell
docker compose stop postgres
```

The development database is exposed on host port `5433` to avoid conflicts
with other local PostgreSQL projects.

## Database Configuration

The application reads the connection string from:

```text
OBSERVABILITY_DATABASE_URL
```

Create the local environment file from the example:

```powershell
Copy-Item .env.example .env
```

The committed `.env.example` contains development-only credentials. Real
production credentials must be supplied securely and must not be committed.

## Database Migrations

Apply all migrations:

```powershell
python -m alembic upgrade head
```

Show the current revision:

```powershell
python -m alembic current
```

Roll back one revision:

```powershell
python -m alembic downgrade -1
```

Create a migration after changing ORM models:

```powershell
python -m alembic revision --autogenerate -m "describe schema change"
```

Autogenerated migrations must be reviewed before they are applied.

## Tables

### monitored_services

Stores the identity and description of each monitored service.

A service is uniquely identified by:

- `name`
- `environment`

Supported environments are development, testing, staging, and production.

### telemetry_records

Stores accepted metric, log, and event telemetry.

Important columns include:

- `id`
- `service_id`
- `telemetry_type`
- `source`
- `observed_at`
- `received_at`
- `payload`

The complete validated telemetry record is retained in the JSON payload.
Indexed columns support future incident detection and time-based queries.

## Service Registry API

```text
POST /api/v1/services
GET  /api/v1/services
GET  /api/v1/services/{service_id}
```

Duplicate service identities return HTTP `409 Conflict`. Unknown service IDs
return HTTP `404 Not Found`.

## Persistent Telemetry Flow

1. The API validates the telemetry batch.
2. Each service name and environment is resolved through the service registry.
3. An unregistered service causes the complete batch to be rejected.
4. UUIDs are generated for accepted telemetry records.
5. The complete batch is inserted in one database transaction.
6. A failed insert rolls back the complete batch.
7. The API returns HTTP `202 Accepted` after the transaction is committed.

## Health Check

```text
GET /health/db
```

A successful response confirms that the application can execute a query
against its configured database.

## Testing

Database tests use a fresh in-memory SQLite database for each test. FastAPI's
database dependency is overridden so tests remain isolated from development
PostgreSQL data.

GitHub Actions additionally starts PostgreSQL and applies all Alembic
migrations before running the test suite.
